# 技術検証と全体アーキテクチャ

調査日: 2026-08-21

## 結論

最小構成は次の通りです。

```text
CoreS3 / GC0308
  320x240 RGB565
       |
       | JPEG変換 + HTTP MJPEG（映像は保存しない）
       v
手持ちPC
  OpenCV -> YOLO軽量モデル（personのみ） -> ByteTrack（一時ID）
       |
       | 通過・立ち止まり・来訪・滞在イベントだけを保存
       v
SQLite -> ローカルWebダッシュボード
```

## 1. 現在の環境

- PC: Apple Silicon Mac、macOS、Python 3.9.6、Node.js 24.14.1
- `apps/stack-chan-cores3/` に、実機確認済みの相棒AIファームウェアと復旧可能なソースがある
- 既存プロジェクトは独立Gitリポジトリで、確認時点の作業ツリーはクリーン（`f2f6dde`）
- `arduino-cli` とPlatformIOは未導入
- 調査時点ではCoreS3がUSB接続一覧に見えていない

システム全体にはグローバルな `arduino-cli` / PlatformIOはないが、既存Stack-chanプロジェクト内には専用PlatformIO環境がある。本PoCも既存プロジェクトを変更せず、別の専用環境・別ファームウェアとして作成する。

この分離は意図的である。既存ファームウェアはマイク、スピーカー、近接・環境光、IMU、サーボ、LittleFS表示を同時利用している。公式CoreS3カメラ初期化は内部I2Cをカメラへ引き渡すため、いきなり統合すると既存機能との競合原因が増える。最初はカメラだけのファームウェアでSTEP 1・2を通し、安定性を確認してから統合可否を判断する。

## 2. CoreS3との接続方法

- USB-C: ファームウェア書き込み、シリアルログ、既存フラッシュのバックアップ
- Wi-Fi: カメラ映像の送信
- CoreS3とPCは同じ2.4GHz Wi-Fiに接続する
- イベント会場Wi-Fiが端末間通信を禁止している場合は、手持ちスマートフォンのテザリングを代替にする

CoreS3はWi-Fiを内蔵し、GC0308（約0.3MP）、16MB Flash、8MB PSRAMを搭載する。公式情報は [M5Stack CoreS3製品ドキュメント](https://docs.m5stack.com/en/core/CoreS3) と [M5Stack公式M5CoreS3ライブラリ](https://github.com/m5stack/M5CoreS3) を参照。

## 3. 映像をPCへ送る方法

採用: HTTP MJPEG。

理由:

- ブラウザとOpenCVの両方から読みやすい
- RTSPやWebRTCよりCoreS3側の実装と切り分けが簡単
- GC0308はJPEGを直接出さないため、CoreS3側で各RGB565フレームをJPEG化する
- 320x240から開始し、帯域と安定性を優先する

CoreS3向けの既存事例として [M5StackCoreS3_CameraWebServer](https://github.com/GOB52/M5StackCoreS3_CameraWebServer) があり、Wi-Fi経由のブラウザ配信が実証されている。本PoCは顔関連機能を含めず、M5Stack公式ライブラリのカメラ初期化を使う最小構成にした。

## 4. 人物検出・追跡方法

初期選択:

- 検出: Ultralytics YOLOのnanoモデル、COCOの `person` クラスだけ
- 追跡: ByteTrack
- 入力: CoreS3のMJPEGストリーム
- 推論: PC上のローカル処理
- ID: 起動セッション内だけの `person_001` 形式。永続的な人物IDにはしない

ByteTrackは外見の再識別を使わない軽量な追跡方式で、固定カメラの最初の基準に向く。Ultralytics公式の [Multi-Object Tracking](https://docs.ultralytics.com/modes/track/) でも、最速・最小構成の開始点として案内されている。

ByteTrackのIDが一瞬だけ切り替わる場合に限り、1.25秒以内かつ画面対角の18%以内に現れた近接トラックを同じセッション匿名IDへ引き継ぐ。長く画面外へ出た人物や離れた位置の人物を同一人物とは推定せず、顔・服装による再識別も行わない。

注意: Ultralyticsの配布条件はAGPL-3.0/Enterprise License。ローカルPoCには採用するが、外部配布や商用製品化の前にライセンス確認を行う。必要ならONNX Runtime + 別実装の検出器・追跡器へ差し替える。

## 5. 匿名イベントモデル

保存するもの:

- 日時
- セッション内の匿名トラックID
- `pass` / `stop` / `visit` / `exit` イベント
- 滞在秒数
- 実施中の施策A/B

保存しないもの:

- 動画、静止画、顔画像
- 顔特徴量
- 氏名などの個人識別情報
- 性別、年齢、人種・民族、感情の推定

ダッシュボードへ映像を表示する場合も、メモリ上の直近フレームだけを使う。

## 6. 段階的な実装順

1. MJPEG配信とPC表示を30分連続確認
2. 人物検出と一時ID表示
3. 1本の仮想ラインを使う通過カウント
4. 10往復テストを複数回行い、方向と重複を調整
5. 注目ゾーンと2秒停止判定
6. ブースゾーン、来訪、退出、滞在時間
7. SQLite集計とWebダッシュボード
8. 10/30/60分集計、テストモード、A/Bテスト
9. 余力があればStack-chan表示演出

現在の最小ブース判定は、画面右側30%を紫の仮ゾーンとする。最初からゾーン内にいる人物は来訪にせず、ゾーン外で確認済みの匿名IDが内側へ入った時点で来訪、外へ出た時点で滞在時間を確定する。ゾーン位置を変更・保存するGUIは次段階で追加する。

## 7. 想定する限界と代替案

- 0.3MPかつ画角が狭いため、混雑時の重なりや遠距離の人物には弱い
- 1台の単眼カメラでは、ゾーン境界付近の奥行きを厳密には判定できない
- 一度完全に隠れた人物は別IDになり、重複することがある
- 会場照明、逆光、Wi-Fi混雑で精度とFPSが落ちる

PoCではカメラを固定し、人物の全身または上半身が十分大きく映る位置、斜め上から通路とブース境界の両方が見える位置を優先する。混雑が激しい場合の現実的な代替案は、手持ちPCのWebカメラまたはスマートフォン映像を入力に使い、解析部分をそのまま再利用すること。
